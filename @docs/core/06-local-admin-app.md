# 06. Local admin app (the agent's own interface)

Status: built (`app/apps/admin` and `app/apps/server`; screens Overview, Mail (home), Messengers (Chats, Settings), Activity, Knowledge, Settings (Sending, Checks, Mail, Agent, Connections, This Mac), Help; Client planned). Next.js (decision 0015). English UI only.

## What
A small local web app (Next.js + React) on the owner's Mac. It shows what the agent did and holds the owner's decisions, nothing else (decision 0025): the drafts the agent left unsent in Mail, each with its reason and checks; what the agent did with every client, one group per session; the project's standing. The owner reads, then sends one draft at a time (or the Checked drafts of one batch with Send all Checked, one at a time on the server, P85b: `14-bulk-send-interface.md`), skips, holds, marks done, flags a client or stops sending. Preparing (choosing clients, a brief, enrolling in follow-ups, sorting) is a phrase in a session; the admin has no form for it and shows the result. The agent may also change the app's own screens while the owner uses it (live edit); the dev server's hot reload shows the change at once.

Agents reach Mail and Notion through their own connectors (`mail-mcp` for Apple Mail, the session's Notion connector); the hub gives them local tools (`draft_write`'s record and `client_record` (hub mcp), `hub sequences`, the knowledge MCP, the `hub` MCP with `draft_write` for Mail drafts, the guard) and the database; the admin shows the state those leave.

It replaces a hosted helper app and, over time, the screens of a hosted back office that the agent now covers.

## Why local
- No hosting, no auth layer, no deploy chain: one owner, one Mac.
- The agent can read and edit the code of the app it serves; a hosted app cannot be changed that way.
- Data stays on the Mac: mail in Apple Mail, working state in `data/app.db` and `state/` under `HUB_HOME`, Notion through its MCP.

## One source per fact (decision 0009)
Notion is the one place for client records; Mail is the one place for the text of a draft. The admin database
holds only what exists nowhere else.

| Data | Lives in | Admin database |
|---|---|---|
| Client profile, leads, tasks, documents (reports are documents, decision 0022) | Notion (the agent writes it through the connector) | only the key: a `clients` row (project, email, name, replies owed, last contact, `updated_at`), made when the agent records a draft for that client. Nothing is copied in bulk; there is no sync |
| Draft text | Mail (an unsent draft the person edits and sends) | no copy: `drafts.body` is empty for a recorded draft (an optional 240-character preview at most); `mail_ref` points at the message |
| Draft review state ("I read the checks", done, hold, skipped), marks, batches, sequence enrolments, follow-up plans and sweeps (decision 0050), the agent's run log | admin database only | yes |
| Project facts, filters, knowledge | files under `<projects folder>/<slug>/` (`<HUB_HOME>/projects`; see `08-local-app-stack.md`) | an index rebuilt from them |

A session reports each unsent draft it leaves with `draft_write`'s `record` (hub mcp, P129 A3; one JSON answer,
0 only when it says `"ok":true`). The command writes straight to the database (no server needed), makes the client row if
it is missing, and keeps one open draft per client: the same `mailRef` again updates it, another one marks the old draft
`skipped` and inserts the new one. It never deletes a client (marks and the log hang on that row) and never writes `sent`.
Sent detection (`14`) finds a recorded draft in the project's Sent mailbox in Apple Mail once the person has sent it from Mail, by its own recorded Message-ID only. A reply in its thread that is not the Hub's (a teammate on a shared mailbox), or another person's Notion `Last sent by` newer than the client's last message, is one line on the open card ("… · your draft may be out of date", P90); it never changes the draft.
Because Notion owns the client record, the admin has no company or deal-value column, no "High value" filter and no `{company}` placeholder.

### Manual reply editor

When a client has written and no unsent draft exists, Mail shows the owner's Markdown editor alongside the conversation. It has formatting actions and a live preview, keeps the saved value as Markdown/plain text, and supports Cmd/Ctrl+Enter and Escape. Saving calls `POST /api/projects/:slug/clients/:id/draft`, which writes one unsent draft through the same Mail writer as agent drafts; it never sends. `Prepare reply` remains the optional agent path, and the send door remains a separate owner confirmation.

## The routes behind the screens
Everything the server answers here is local: the database, the project folders and the server's own loops, read in the request. No route reads Mail or Notion to show a number, so no number carries a freshness stamp.

A refusal is `{ error, code }` (`@hub/contract/errors`). Every refusal the Hub states is a `HubError` (`@hub/config/errors`, P126 E1) whose kind gives the status: `invalid` 400, `not_found` 404, `wrong_state` 409, `unavailable` and `busy` 503, `forbidden` 403, `upstream` 502 (wire code `server`). The server's `onError` answers it, so a route catches only to add words (a Telegram or WhatsApp failure is named, Mail's slow save is explained) or a header (`retry-after` on a second core check, 429). A repository's `invalid` is 400 and its `unknown_project` 404.

| Route | What it does | Cost |

## Live updates (P50, decision 0028 in the owner's plan repo)
While the agent works (in the terminal column or another window) the screens update by themselves, within about a second, with no reload:
- **What changed is written by the database itself.** Migration 0019 gives every table three triggers (insert, update, delete) that bump one counter (`live_seq`) and record `(table, project, counter)` in `live_versions`, inside the writer's own transaction, whoever writes: the server, `draft_write`'s record in a terminal, a migration, `sqlite3` by hand. A rolled-back write records nothing. The table holds one row per table and project, so it never needs pruning and every counter stays a resume point. What is not a row is watched by the server and bumped through the same path (`bumpTopic`): the pollers' state (`health`), the Connections files (`connections`, so a `hub token` in a terminal shows at once) and, per project, the agent session log's day files (`agent-log`, P59: a watch with one signature per project folder of `state/log`, every 500 ms; the `.cursor/` folder is not compared), the LaunchAgent (`autostart`, P67: `state/autostart/starts.jsonl`, the off file and the switch, every second; not its log), and the core update check (`core`, P68: a finished check or a changed `state/core-update.json`, every second). A new table needs its triggers in its migration; `packages/db/test/live.test.ts` fails without them, and the server's `Record<LiveTable, LiveTopic>` fails `tsc`.
- **The server tails it.** Every 200 ms it reads the counter (one page); when it moved, it reads the changed rows, maps each table to one of 13 topics (`@hub/contract/live`), waits 100 ms to merge a burst, and sends one frame on `GET /api/live`. A client still busy with the last frame gets one `reset` instead of a queue.
- **The admin invalidates, it is never pushed data.** One tab per browser holds the Web Lock `hub-live` and opens the EventSource (HTTP/1.1 allows about six connections per origin across all tabs); it passes every frame to the other tabs over a `BroadcastChannel`. Each tab invalidates the query keys of the frame's topics (`TOPIC_KEYS` in `apps/admin/src/lib/cache/keys.ts`, the one key factory), so only what changed is read again, through the normal API and its contract parse. A hidden tab only marks its queries stale; its focus refetch catches up. A row change never reads Mail (decision 0013): the open draft's text in Mail is read on open, on focus and on the one Mail topic, `mail`, which `draft_write` bumps after it wrote a draft of the project (P53), so a revision by the agent shows on the open card within about a second plus the Mail read. When the agent re-recorded the draft under an open card, the card also says "Changed by the agent since you opened it" with Reload. When Mail holds more than one draft of the thread, the card shows the one the Hub recorded (else the newest) and names every Mail id, saying which one the Hub wrote, so the owner keeps one; that text has no hash, so it cannot be Checked and the send refuses it. The address names the card on screen: a wide pane replaces a bare `/mail` with the first row's `/mail/<id>` (routes rule 9). New Activity rows at the top of the timeline are announced in a polite live region ("2 new").
- **The agent activity feed (P59, P73).** No feed rows in the sidebar since P73 (decision 0037): they repeated Activity's draft writes and the strip's dot. What stays is the signal, read from `GET /api/projects/:slug/agent-feed` (the tail of the session log: [25-agent-log.md](25-agent-log.md)), refetched on the topic `agent-log`: the terminal strip's dot (and the phone's terminal button) takes the attention colour while the agent waits on the owner, until he opens the column; one tone per turn that ended (attention, ready, problem; synthesised by `@hub/ui/sound`, muted by the speaker switch in the footer; only the tab holding Web Lock `hub-sound`, after a click in it, plays, and that tab refetches the feed even when hidden).
- **The fallback is the pulse.** The Mail status line says "Live" while the stream is up and "Reconnecting, data may be old" after 5 s without it. While it is down, the page polls `GET /api/pulse` every 10 s as before P50 and refetches every list when the database file moved; a stream the server cut (a restart: the `/api` rewrite answers 500) is opened again after 1, 2, then 5 s, resuming after the last frame the page applied. The Activity and Overview timers are gone.
- **Through the `/api` rewrite.** The stream goes through Next's rewrite like every call, so `proxy.ts` and the Host guard apply unchanged and no ticket is needed (a cross-origin page cannot read a same-origin stream without CORS). `Cache-Control: no-cache, no-transform` is load-bearing: without it Next gzips the proxied stream and holds every frame (measured in the L0 spike: 0 frames in 8 s; with it 1 to 4 ms per frame, and a stream with only 15 s pings stayed open past 165 s under the 120 s `proxyTimeout`).

## What a screen shows by default
Each screen opens on what the next decision needs and keeps the rest one step away (`app/@rules/admin-principles.md`). Above the list sits one status line, never a paragraph or an accordion. ## Rules
- The agent only creates drafts. The app sends only when a person confirms one draft (decision 0011, `16` section 3B): Send on a ready draft whose checks the person read ("I read the checks", bound to the Mail text they saw), with the exact mail shown first, through the one route `POST /api/projects/:slug/drafts/:id/send`, whose apply needs the page's single-use ticket. Bulk = many drafts, never sent in bulk.
- The terminal column (always there; when no tab can start it says why and the fix, P66) runs Claude Code, Codex or the owner's shell for the project in the URL; opened, it starts the best ready CLI by itself (P57: Claude Code first, one line when it fell back); it is a viewing preference, never URL state ([24-terminal.md](24-terminal.md)): the active tab in `localStorage`, the open state and width in the `hub_shell` cookie beside the sidebar's pin and the last breakpoint, which the shell layout reads on the server so a cold load is laid out as the last page ended, the column at its width while the terminal read loads (P128 X8). A file dropped on the open tab is copied into the instance and its path pasted into the input line (P76); a file dropped anywhere else in the admin does nothing, it never opens in the tab.
- Bind to 127.0.0.1 (`next dev -H 127.0.0.1`: without the flag Next listens on every address); no remote access in the first version. Next has no DNS-rebinding guard of its own, so `src/proxy.ts` refuses any Host that is not a loopback name and any write whose Origin is not; the API repeats the check.
- The tab publishes what it shows (P51, P72): every route its id and its own title, and refs, through one channel (`lib/focus.ts`): rows carry `data-agent-ref` (`agentRef(ref)`; drafts, Activity's lines (the draft a line names, else its client: P73), Knowledge's entries, Overview's projects), a record a screen opens that its address does not name goes through `useFocusSubject`, picked rows through `useFocusSelection`, and two observers on `#main` add the row he clicked or arrowed to (never hover) and the rows on screen. A new screen needs nothing else; a new ref kind adds one resolver in `@hub/agent/focus`. The agent reads it as "this entry", "this client" through `hub mcp` and the prompt hook; nothing of it is URL state, and only refs leave the browser ([24-terminal.md](24-terminal.md)).
- The agent may point, never act (P72, decision 0038): its `highlight` draws a ring and "Agent: <note>" on up to five rows for 30 s (`@hub/ui/product/spotlight`, `features/focus/pointer.tsx`), announced politely, scrolled into view once and never while he types; Escape, a click or a route change removes it. A row on another screen is offered in the dock header ("Agent points at … · Show"); only his click navigates.
- Open and Reveal (P61) show a fact in the program that holds it (Mail, Notion, Finder, the file's own app) and change nothing in the Hub. One registry declares them (`@hub/contract/local`); Mail and Notion are plain links, a file or folder goes through `POST /api/local/:action` with a key. `hub open` is the owner's terminal form; the agent is denied it and a bare `open` (`app/@rules/admin-principles.md` rule 1).
- English only, per the owner.
